# Leanputer ノード遷移機械 IR 仕様案 v0.1

Nov 20, 2026 · @Syumei

## 1. 目的と範囲

この仕様は、Lean カーネルを「1遷移 = 1 forward」で実行する抽象機械として書くための IR を定める。決めるのは2つで、1遷移に許す読み書き・分岐・演算の上限（遷移の型）と、そこから層数とパラメータ数を重み生成の前に計算するコストモデルである。

現行 IR との違いは次のとおり。

|  | 現行（d3250a9） | 本案 |
| --- | --- | --- |
| 状態 | 951 レジスタ | 14 レジスタ（§2） |
| 操作の単位 | 16bit ワード | セル（タグ + 3語） |
| 規則の単位 | 73 族 / 6,454 効果 | 遷移行（位相 × ガード） |
| forward / semantic step | 約170（230,432 / 1,355） | 1（型で保証） |
| コストが分かる時点 | lowering 後 | 遷移表を書いた時点 |

- **対象。** v0.1 は WHNF（β・δ・ζ）の遷移表で型を確定する。conversion、型推論、帰納型の受理は同じ型の上に後から載せる。
- **対象外。** 重みへの具体的な lowering、BF16 上の数値的厳密性、検査器全体の形式的健全性。
- **維持する前提。** stock Qwen3\_5ForCausalLM、GDN キャッシュ、identity hidden feedback。ホストは構文を運ぶだけで、意味的な判断をしない。
- **位置づけ。** 未実装の提案である。§5 の数値は式による見積もりで、測定結果ではない。

## 2. 機械モデル

状態は 14 個のレジスタと 3 つのメモリバンクだけで、ルーチンごとの局所変数はすべてバンク上のセルに置く。語は 16 bit、番地 0 は null とする。

### レジスタ

| レジスタ | 幅 | 役割 |
| --- | --- | --- |
| pc | 12 bit | 位相（EVAL、LOOKUP、RET など） |
| status | 4 bit | RUN / DONE / INVALID / RESOURCE。RUN 以外は吸収状態 |
| flags | 8 bit | モード（δ 展開の可否など）。conversion 用に予約 |
| C | 1語 | 注目している項セルの番地 |
| E | 1語 | 環境の先頭セルの番地 |
| K | 1語 | スタック頂上の位置 |
| V | 1語 | 返す値セルの番地 |
| A0, A1, A2 | 各1語 | 作業用（ループのカウンタや中間番地） |
| U | 1語 | 宇宙レベル環境。δ 展開時のレベル引数用に予約 |
| lvl | 1語 | 束縛の深さ。conversion 用に予約 |
| hp | 1語 | ヒープの割り付け位置 |
| fuel | 1語 | 残りステップ数 |

WHNF が使うのは pc、status、C、E、K、V、A0、A1、hp、fuel の 10 個である。

### メモリバンク

| バンク | 規律 | 中身 |
| --- | --- | --- |
| heap | 追記のみ。割り付け後に変わるのは memo 語だけで、書くのは1回 | 項、環境、値 |
| stk | LIFO。読めるのは頂上だけ | 継続フレーム |
| decl | 受理済みの宣言。検査中は読み取り専用 | 種別、型、値 |

### セル

heap の1行は `(tag, a, b, c, m)` の 5 語（80 bit）で、GDN の1行（データ 126 bit）に収まる。tag 語は下位 6 bit がタグ、1 bit が「memo 有効」である。stk の1行は `(kind, a, b)`。

| 種類 | 形 | 意味 |
| --- | --- | --- |
| 項 | BVAR(i)、SORT(l)、CONST(c, ls)、APP(f, x)、LAM(ty, body)、PI(dom, cod)、LET(ty, val, body) | 入力構文。現行 arena の Expr タグの一部（LOCAL・PROJ・リテラルは未対応） |
| 環境 | ENV(tm, env, next) + memo | 未評価の項 tm とその環境。memo は評価済みの値 |
| 値 | CLO(tm, env) | λ・Π・Sort の閉包 |
| 値 | NEU(head)、NAPP(fn, tm, env) | 展開できない定数と、それへの適用 |
| フレーム | F\_HALT、F\_APP(tm, env)、F\_UPD(cell) | 停止、保留中の引数、memo の書き戻し先 |

置換は行わない。β 簡約は ENV セルを1つ割り付けるだけで、shift・subst・lift の走査がなくなる。

不変条件は2つ。heap のセルは割り付け後に書き換えない。memo に入るのは、その ENV セルの `(tm, env)` を簡約した値だけである。環境の要素は閉じているので、memo は文脈に依存しない。

## 3. 遷移の型

遷移表の1行は「位相 pc とガードが成り立つとき、次の状態はこれ」という規則で、1行の実行がちょうど 1 forward になる。そのために、すべての行が次の 8 つの規則を満たす。

1. **読み計画は pc で決まる。** どのポートでどの番地を読むかは pc だけの関数とする。例外として、第2ラウンドの番地は第1ラウンドで読んだセルのタグで選び分けてよい。
2. **読みは上限付き。** ポート数と、読んだ値を番地にしてさらに読む深さを、下のプロファイルで固定する。
3. **ガードは有限表引き。** 分岐に使えるのは、読んだセルのタグ（memo 有効ビットを含む）、flags、述語ビットだけである。述語は語どうしの EQ・LT と小さい定数との比較に限る。
4. **書きは上限付きで、番地が限られる。** heap は1行。hp への割り付けか、同じ遷移で読んだ行の memo 書き戻しのどちらか一方とする。stk は push・pop・頂上の置き換えのうち1つ。
5. **次の値はメニューから1つ選ぶ。** レジスタと書き込みセルの各語は、レジスタ、読んだセルの語、hp、即値、ALU レーンの出力のどれかそのままである。演算の連鎖は許さない。
6. **同時代入。** 右辺はすべて遷移前の値を見る。dirty queue も commit 段も持たない。
7. **資源ガードは共通。** fuel 切れ、heap 満杯、stk 満杯は全遷移共通の回路で検査し、RESOURCE に落とす。行ごとの述語上限には数えない。
8. **1遷移 = fuel 1。** 補助ステップという概念がないので、semantic step 数と forward 数が一致する。

上限を超える処理は、コンパイラが複数の遷移に分割するか拒否する。幅を黙って広げることはしない。

### プロファイル P0

| 資源 | 上限 | WHNF 表での最大使用 |
| --- | --- | --- |
| heap 読みポート | 2（A はレジスタ番地のみ、B は依存番地も可） | 2 |
| 依存読みの深さ | 2 ラウンド | 2 |
| stk 読み | 1（頂上のみ） | 1 |
| decl 読み | 1（依存番地可） | 1 |
| heap 書き | 1 行 | 1 |
| stk 書き | 1 | 1 |
| 述語ビット | 3 | 2 |
| ALU レーン（語 ± 語、語 ± 小定数） | 2 | 1 |

「最大使用」は §8 のシミュレータが実行時に数えた値である。conversion が2つの値を同時に辿るには heap ポートが 3 本要るかもしれず、その場合は P0 を改訂する。ポートを1本増やすと heap の複製が1つ増える。

## 4. 記述形式

遷移表はデータとして書き、同じ表を参照インタプリタ、静的検査、重みコンパイラの3つが読む。仕様と実装を別々に書かないので、両者がずれる余地がない。

位相ごとに読み計画を1つと、ガード付きの行を並べる。EVAL の一部を示す。

```
phase EVAL
  read n = heap.A[C]
  read e = heap.B[E]
  read k = stk.top
  read d = decl[n.a]            when n.tag = CONST

  row E-app      : n.tag = APP
      push F_APP(n.b, E)
      C := n.a
      goto EVAL

  row E-beta     : n.tag = LAM, k.kind = F_APP
      alloc h = ENV(k.a, k.b, E)
      pop
      C := n.b ; E := h
      goto EVAL

  row E-var-walk : n.tag = BVAR, e.tag = ENV, n.a != 0
      A0 := n.a - 1 ; A1 := e.c
      goto LOOKUP

  else INVALID
```

意味論は次のとおり。

- `read` はその位相の全行で共通である。`when` は第2ラウンドの選び分け（規則 1 の例外）を表す。
- 行の右辺はすべて遷移前の値を参照する。書かなかったレジスタは値を保つ。
- `alloc h = ...` は hp の位置にセルを書き、h をその番地に束縛し、hp を 1 進める。
- `goto` を省いた行は同じ位相に留まる。
- 1つの位相の行は互いに排他で、`else` を含めて網羅的でなければならない（§6）。

重みの上では、1行が FFN のマッチユニット 1 個に対応する。ユニットは pc・タグ・述語ビットの組に一致したときだけ発火し、その行の制御語（どの供給元をどこへ流すか）を出す。現行のページ式 ROM が PC の一致で 112 bit レコードを出すのと同じ仕組みで、照合キーにタグと述語が加わる。

## 5. 1 forward の段構成とコストモデル

層数は「固定段 9 層 + メモリ層 + 遷移表の大きさで決まる層」で、遷移表とプロファイルから重み生成の前に計算できる。WHNF だけなら 16 層という見積もりになる。

### 段構成（GDN バックエンド）

| 順 | 段 | 層数 | 内容 |
| --- | --- | --- | --- |
| 1 | 作業列のクリア | 3 | 前の forward の一時値を打ち消す |
| 2 | 読み計画 | 2 | pc から第1ラウンドの番地を選ぶ |
| 3 | 第1ラウンドの読み | heap A のページ層 + stk 1 | 前の遷移の保留書き込みもここで反映する |
| 4 | 第2ラウンドの番地選択 | 1 | タグで選び分ける |
| 5 | 第2ラウンドの読み | heap B のページ層 + decl 1 |  |
| 6 | 述語と ALU | 2 | 比較レーンと加減算レーンを並列に |
| 7 | 遷移の照合 | ⌈N\_rows / I\_eff⌉ | 1行 1 ユニット。制御語を出す |
| 8 | 供給元の選択 | ⌈U\_mux / I\_eff⌉ | 次のレジスタ値と書き込みパケットを作る |
| 9 | 出力境界 | 1 | hidden feedback へ渡す |

メモリ層と FFN の仕事は同じ層に同居できるので、単純な合計は上限である。

### 式

```latex
L = 9 + R\left\lceil \frac{N_{heap}}{128\,V} \right\rceil + 2 + \left\lceil \frac{N_{rows}}{I_{eff}} \right\rceil + \left\lceil \frac{U_{mux}}{I_{eff}} \right\rceil
```

- R は heap 読みポート数（P0 では 2）、V は1キーヘッドあたりの値ヘッド数、N\_heap は heap の行数。ポートごとに heap の複製を1つ持つ。
- N\_rows は遷移表の行数。
- U\_mux は「宛先のビット数 × その宛先の供給元メニューの大きさ」の総和。メニューを宛先ごとに絞るほど小さくなる。
- I\_eff は FFN 中間幅から列の引き継ぎ用 24 ユニットを引いた値。

パラメータ数は compact-datapath-budget と joint-transition-architecture の式をそのまま使う。GDN 層が 3HI + (258 + 386V)H + 1152 + 514V、その他の層が 3HI + 12H + 4、全体に 129H を足す。この式は現行の 48,290,654 を再現することを確かめた。

### 見積もり

| 構成 | N\_rows | U\_mux | heap 行 | 層数 L | dense パラメータ（H1024 / I512） | dense パラメータ（H768 / I512） |
| --- | --- | --- | --- | --- | --- | --- |
| WHNF のみ（§8 の表） | 24 | 約 600 | 512 | 16 | 30,464,580 | 22,850,884 |
| 全カーネル（仮定） | 3,000 | 2,500 | 512 | 26 | 46,316,140 | 34,739,564 |
| 全カーネル（仮定） | 3,000 | 2,500 | 4,096 | 40 | 94,214,620 | 70,674,652 |

比較対象の現行 d3250a9 は 65 層・48,290,654 パラメータで、1 semantic step に約 170 forward、つまり約 11,000 層評価を使う。本案では 1 step が L 層評価になる。

この表の読み方には注意が 3 つある。

- 全カーネルの N\_rows と U\_mux は仮定で、根拠のある数字ではない。conversion と帰納型受理の表を書くまで分からない。
- H は残差列の見積もり（レジスタ約 220、読んだセル約 290、制御語約 250、書き込みパケット約 160、その他で計約 1,000 列）から 1024 とした。列の寿命を詰めれば 768 に収まる可能性がある。
- heap を 512 行から 4,096 行に増やすと 14 層増える。GDN バックエンドでは容量が層数に直結する（§10）。

## 6. コンパイラの静的検査

コンパイラは重みを出す前に次の 6 項目を検査し、1つでも落ちたら生成を拒否する。検査は遷移表とプロファイルだけを入力とし、証明や宣言のデータを読まない。

1. **上限。** すべての行が §3 の規則 1〜8 とプロファイルの上限を満たす。
2. **網羅性と排他性。** 各位相で、タグ・述語・flags のどの組合せにもちょうど1行が一致する。一致する行がない組合せは明示の `else INVALID` に落ちる。
3. **番地の型。** セルの各語に「heap 番地」「宣言番号」「自然数」「即値」の種別を宣言し、読みの番地に使えるのは対応する種別の語だけとする。種別はガードで確定したタグから決まる。
4. **書き込みの規律。** heap の書き込み先は hp か、その遷移で読んだ行である。memo の書き戻しは memo 語と有効ビット以外を変えない。
5. **停止状態。** DONE・INVALID・RESOURCE は吸収状態で、どの行もそこから出ない。DONE に入れる行は表の中で明示的に印を付けたものだけである。
6. **予算レポート。** N\_rows、U\_mux、制御語の幅、残差列の最大使用、§5 の式による層数とパラメータ数を出力する。目標（§9）を超えたら生成しない。

項目 6 が現行とのいちばんの違いで、147,402 ユニットのような結果を lowering の後ではなく表を書いた時点で知ることができる。

## 7. カーネルから遷移表を導出する手順

遷移表は手で効果を積み上げず、関数型で書いたカーネルから 5 つの変換で導く。この順に進めると、§2 の「少数レジスタとフレーム」という形が自動的に出てくる。

1. **一階の関数型で書く。** whnf、isDefEq、inferType などを、代数的データ型上の相互再帰関数として書く。古典的な実装（Lean4Lean、nanoda）が下敷きになる。ただし置換の代わりに環境を渡す形に書き直す。δ 展開の順序などの戦略はそれらに合わせる。
2. **ANF にする。** すべての中間値に名前を付け、1つの式が1つのパターンマッチか1つの構築になるようにする。
3. **CPS 変換して脱関数化する。** 「呼び出しから戻った後にやること」が1種類ずつフレームの種別になり、関数本体が位相になる。フレームに保存する変数は、呼び出しをまたいで生きているものだけである。
4. **上限に合わせて分割する。** 1つの位相が P0 を超えたら、読みの途中で別の位相に切る。リストやベクタの走査は「1遷移で 2 要素進むループ位相」にする（§8 の LOOKUP が例）。
5. **大きいフレームは連結する。** 保存する語が 2 語を超えるフレームは、複数の stk 行に分けて積む。積み下ろしの遷移数はその分増える。

導出した表は、既存の Python spec と accept / reject / RESOURCE の結果で差分テストする。簡約の順序が違うので、ステップごとの状態一致は求めない。

帰納型の受理や再帰子の生成のように宣言ごとに1回しか走らない処理も、同じ手順で同じ表に載せる。分割が細かくなって遷移数が増えても、実行時間への影響は小さい。行数（N\_rows）への影響は大きいので、こちらは予算レポートで監視する。

## 8. 例：WHNF の遷移表

β・δ・ζ 簡約による WHNF は、3 位相・24 行で P0 に収まる。この表は Python のシミュレータで実行し、置換ベースの独立した正規化器と結果が一致することを確かめた。引数は必要になるまで評価せず、評価結果は memo に残す（必要呼び）。

### EVAL：項 C を環境 E で簡約する

読みは `n = heap.A[C]`、`e = heap.B[E]`、`k = stk.top`、n が CONST のとき `d = decl[n.a]`。

| 行 | ガード | 動作 | 次 |
| --- | --- | --- | --- |
| E-app | n = APP(f, x) | push F\_APP(x, E)。C := f | EVAL |
| E-beta | n = LAM、k = F\_APP(x, ρ) | alloc h = ENV(x, ρ, E)。pop。C := body、E := h | EVAL |
| E-clo | n = LAM かつ k ≠ F\_APP、または n = PI、SORT | alloc h = CLO(C, E)。V := h | RET |
| E-zeta | n = LET(ty, val, body) | alloc h = ENV(val, E, E)。C := body、E := h | EVAL |
| E-var0-memo | n = BVAR(0)、e = ENV（memo 有効） | V := e.m | RET |
| E-var0-force | n = BVAR(0)、e = ENV（memo なし） | push F\_UPD(E)。C := e.tm、E := e.env | EVAL |
| E-var-walk | n = BVAR(i)、i ≠ 0、e = ENV | A0 := i − 1、A1 := e.next | LOOKUP |
| E-delta | n = CONST、d = 定義 | C := d.value、E := null | EVAL |
| E-stuck | n = CONST、d = 公理 | alloc h = NEU(C)。V := h | RET |
| else |  | status := INVALID |  |

### LOOKUP：環境を 1 遷移で 2 要素ずつ辿る

読みは `p = heap.A[A1]`、`q = heap.B[p.next]`。q が依存読みである。

| 行 | ガード | 動作 | 次 |
| --- | --- | --- | --- |
| L-hit0-memo | A0 = 0、p = ENV（memo 有効） | V := p.m | RET |
| L-hit0-force | A0 = 0、p = ENV（memo なし） | push F\_UPD(A1)。C := p.tm、E := p.env | EVAL |
| L-hit1-memo | A0 = 1、p = ENV、q = ENV（memo 有効） | V := q.m | RET |
| L-hit1-force | A0 = 1、p = ENV、q = ENV（memo なし） | push F\_UPD(p.next)。C := q.tm、E := q.env | EVAL |
| L-walk2 | A0 ≥ 2、p = ENV、q = ENV | A0 := A0 − 2、A1 := q.next | LOOKUP |
| else |  | status := INVALID |  |

### RET：値 V をスタック頂上のフレームに返す

読みは `k = stk.top`、`v = heap.A[V]`。ポート B は k の種別で選び分け、F\_APP なら `t = heap.B[v.tm]`、F\_UPD なら `u = heap.B[k.cell]` を読む。

| 行 | ガード | 動作 | 次 |
| --- | --- | --- | --- |
| R-halt | k = F\_HALT | status := DONE |  |
| R-update | k = F\_UPD(cell) | u の memo に V を書き戻す。pop | RET |
| R-beta | k = F\_APP(x, ρ)、v = CLO(tm, env)、t = LAM | alloc h = ENV(x, ρ, env)。pop。C := t.body、E := h | EVAL |
| R-napp | k = F\_APP(x, ρ)、v = NEU または NAPP | alloc h = NAPP(V, x, ρ)。pop。V := h | RET |
| else |  | status := INVALID |  |

照合ユニットの数え方では、E-clo が 3 行、R-napp が 2 行になり、else を含めて 24 行である。

### シミュレータでの確認

- **結果の一致。** 手書きの 13 項とランダム生成の 300 項で、機械の結果を読み戻した項が WHNF であり、参照実装と同じ正規形を持つことを確かめた。
- **不正入力。** 未束縛変数、Sort や Π への適用、未知の定数の 5 例がすべて INVALID になった。
- **上限。** 全遷移で P0 の上限を実行時に検査し、違反はなかった。最大使用量は §3 の表のとおり。
- **共有の効果。** 評価の重い引数を 8 回使う項で、memo ありは 189 ステップ、memo なしは 1,911 ステップだった。

| 項 | ステップ | 割り付けた heap セル | スタック最大深さ |
| --- | --- | --- | --- |
| (λx. x) s | 6 | 2 | 1 |
| Church 数の 2 + 2 を s、z に適用 | 28 | 9 | 4 |
| Church 数の 3 × 4 を s、z に適用 | 35 | 12 | 4 |
| de Bruijn 添字 6 の参照 | 21 | 8 | 7 |

これらは型も宇宙レベルもない小さな閉じた項での結果で、Lean の実入力での測定ではない。δ 展開は常に行う設定で、Lean の遅延 δ はまだ扱っていない。

## 9. 測定ゲートと進め方

最初の 2 つのゲートは重みを1つも作らずに通過でき、この設計が成り立つかどうかはそこでほぼ決まる。モデルの生成と GPU 実行は G2 以降に限る。

| ゲート | やること | 重み | 合格条件 |
| --- | --- | --- | --- |
| G0 | ground fragment（Sort・Pi・Lam・App・let、βδζ、η、proof irrelevance）の conversion と型推論を表に書き、参照インタプリタで既存コーパスを実行する | 不要 | 既存 spec と accept / reject が全件一致。ステップ数、heap 消費、スタック深さを記録 |
| G1 | G0 の表で予算レポートを出す | 不要 | 層数 40 以下、dense パラメータ 48,290,654 以下 |
| G2 | WHNF の表（§8）だけを stock モデルに lowering する | 必要 | 全ステップで参照と全レジスタ・全バンクが一致。forward 数 = ステップ数。forward/s を実測 |
| G3 | ground fragment 全体を lowering し、同じ original-source の組を検査する | 必要 | accept / reject が一致。現行の 230,432 forward・800 秒と比較 |
| G4 | 帰納型受理、再帰子生成、記号的宇宙レベルを表に載せる | 必要 | 73 族の現行規則と同じ入力領域で G1 の予算を維持 |

打ち切りの基準も先に決めておく。

- G0 で heap 消費が目標容量を大きく超えたら、GDN バックエンドのまま進めず、§10 の容量の項目を先に解く。
- G1 で予算を超えたら、P0 の改訂は 1 回までとする。それでも超えるなら、幅を広げて通すのではなく設計を棄却する。

## 10. 未解決事項とリスク

いちばん大きいリスクは heap の容量で、次が Lean の定義的等価性判定との挙動の差である。どちらも G0 で数字が出る。

- **heap の容量。** heap は追記のみで回収しないので、消費はステップ数に比例する（§8 の例では 3 ステップにつき約 1 セル）。heap512 は千数百ステップで尽きる計算になる。GDN バックエンドでは容量を増やすと層が増える。対策の候補は、宣言の検査が終わるたびに hp を巻き戻すことと、heap をトークン列に追記して full-attention 層で読むバックエンドである。後者は RoPE と softmax の厳密性が未検証。
- **Lean との挙動の差。** Lean のカーネルは定義の高さを見て δ 展開を遅らせる。環境機械でこれを再現しないと、Lean が短時間で通す証明が fuel 切れになりうる。flags の δ モードで whnf\_core 相当と完全な whnf を分ける想定だが、表はまだない。research-plan に「naive lazy は悪化した」という記録がある点にも注意する。
- **conversion が P0 に収まるか。** 2 つの値を並行して辿るので、heap ポート 3 本が要る可能性がある。束縛の下に入るときの新しい変数は、de Bruijn レベルを持つ値セルとして追加する想定である。
- **行数が読めない。** 帰納型受理と再帰子生成を表にしたときの N\_rows は、書いてみるまで分からない。§5 の 3,000 は仮定である。
- **memo の書き戻し。** GDN では書き込みが次の forward の読みの直前に反映される。割り付けた直後のセルと、memo を書いた直後の行を次の遷移で読む場合のタイミングを、ポートごとの複製すべてで確かめる必要がある。
- **環境の線形探索。** de Bruijn 添字 i の参照に約 i / 2 遷移かかる。束縛が深い項で支配的になるなら、環境の表現を見直す。
- **残差幅。** 約 1,000 列という見積もりは手計算で、列の寿命割り当てをしていない。
- **宇宙レベル。** δ 展開時のレベル引数は、置換せずにレベル環境 U で運ぶ想定だが、レベルの比較と正規化の表は未着手である。
